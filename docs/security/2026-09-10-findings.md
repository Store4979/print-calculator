# Security findings — confirmed against live production, 2026-09-10

Baseline: `30a0aa6` (repo) and project `gmxyisjjaxtpycsmmzef` (live).
Every claim below is tagged **FACT** (observed in the live database or read at a
specific file:line) or **INFERENCE** (reasoning I did not execute). Every live
probe ran inside `begin … rollback`; nothing was changed.

Two corrections to the assumed picture, both of which change the work:

1. **There are two private buckets, not one.** `customer-uploads` (the walk-in
   queue) has **no** `storage.objects` policies at all — direct Storage access
   to it is already closed, and the only way in is the unauthenticated
   functions. `job-files` (attachments on saved `print_jobs`) is the bucket
   carrying `job_files_anon_*`. Scope items 1 and 2 therefore hit **different
   buckets** and neither fix covers the other.
2. **`anon` holds `TRUNCATE` on every public table**, and RLS does not filter
   `TRUNCATE`. This is not in the six-item scope and is a one-line fix.

> **Amended 2026-09-11** after re-pulling the policy evidence to the full
> standard (permissive mode, command, roles, `USING` and `WITH CHECK` reported
> separately, RLS state, table-level grants, and `storage.*`). Three changes,
> all recorded in place below rather than silently overwritten:
>
> - **Finding 2 overstated the DELETE risk.** A SQL `DELETE` on
>   `storage.objects` as `anon` is **blocked by Supabase's own trigger**
>   (`42501 Direct deletion from storage tables is not allowed`), not by the
>   policy. The `job_files_anon_delete` policy still permits deletion through
>   the **Storage HTTP API**, so the finding stands — but "they can destroy the
>   store's saved job files" was written as though plain SQL did it, and it
>   does not.
> - **Finding 7 extends to storage.** `anon TRUNCATE storage.objects`
>   **succeeded, 5 rows → 0**, in a rolled-back transaction. Same latent
>   privilege, same unestablished reachability, and the trigger above does not
>   intercept it.
> - **One feared attack is closed.** `storage.buckets` has RLS on with **zero
>   policies**: as `anon`, `SELECT` returns 0 buckets and
>   `UPDATE ... SET public = true` on `customer-uploads` changed no rows.
>   Despite holding the grant, `anon` cannot flip a private bucket public.
>
> No `USING`-only inference was used on any INSERT policy in the re-pull; on
> INSERT, `USING` is `(null)` by definition and `WITH CHECK` is the only gate.
> Every policy in the project is PERMISSIVE — there is not one RESTRICTIVE
> policy anywhere, which is why a narrow policy added beside an open one
> widens nothing and the open one must be dropped.

## Finding 1 — the three privileged functions authenticate nobody

**FACT.** `netlify/functions/get-download-url.js:18-39` is the whole handler.
It checks the HTTP method, parses `paths`, and calls `createSignedUrl` on each
with the service-role key. There is no `Authorization` header read, no session
lookup, no ownership check, no store scoping. It signs **any path the caller
names** in `customer-uploads`.

**FACT.** `complete-job.js:29-42`: takes `id`, deletes the row's files from the
bucket, deletes the row. No authentication, no ownership check. Destructive.

**FACT.** `send-print-job.js:288` — `to: to || UPS_STORE.email`. The recipient
comes from the request body. With `SMTP_HOST/USER/PASS` configured
(`:273-283`), any unauthenticated caller can send mail **from the store's own
SMTP identity**, with attacker-supplied PDF attachments (`:300+`), to any
address. That is an open relay wearing the store's return address.

**FACT.** `pending_jobs` is readable by `anon`: policy
`anon_select_pending_jobs`, `cmd=SELECT`, `roles={anon,authenticated}`,
`qual=true`. Live probe as `anon`: **3 orders / 1 store / 6 print_jobs
readable**; `pending_jobs` returned **0 rows because the queue is empty right
now**, not because it is protected.

**FACT.** `pending_jobs` is in the `supabase_realtime` publication.

**Confirmed chain.** anon SELECT `pending_jobs` → `files[].path` →
`POST /.netlify/functions/get-download-url` → signed URL → the customer's
file. Every link is present and unauthenticated. Realtime makes it worse than
polling: an attacker can **subscribe** and receive each new job's file paths the
moment a customer uploads, then mint a URL seconds later.

**INFERENCE, not executed.** I did not send a request to the live function. The
chain is confirmed structurally (policy + code read); I did not exfiltrate a
file, and there is currently nothing in the queue to exfiltrate. Signed URLs
last 15 minutes but can be re-minted indefinitely; `cleanup-stale-jobs` removes
files after 24h, so each job's window is up to a day.

**Severity: critical.** Customer documents — résumés, tax forms, legal filings,
medical paperwork — are the most sensitive data this business touches.

**Partial status: the `send-print-job` third of this finding is fixed in this
branch.** The recipient is now resolved server-side from the `stores` record
(service_role, slug from server config), falling back to the compiled-in store
address. A caller-supplied `to` is never read — it is logged as an abuse
signal and discarded — and the client no longer sends one. The endpoint stays
public until Release 2, so it is constrained instead: two attachments maximum,
8 MB each, 12 MB total, 20 MB body, 200-character subject, and a per-IP rate
limit of 5/minute. `scripts/tests/send-print-job.test.js` proves denial with a
**fake transport**; no trial abuse mail was ever put through the production
relay. The rate limiter is per warm instance, so it raises the cost of abuse
rather than guaranteeing a cap — a durable limit needs shared state and is
deferred to Release 2 rather than smuggled in as a migration here.

`get-download-url` and `complete-job` remain unauthenticated. They need the
staff session and device enrollment, so they are Release 2.

## Finding 2 — `job_files_anon_*` exposes the job-history bucket to the world

**FACT.** Live `storage.objects` policies, re-pulled 2026-09-11 to the full
standard. `storage.objects`: `rls = true`, `forced = false`, 3 policies.

| policy | mode | cmd | roles | USING | WITH CHECK |
|---|---|---|---|---|---|
| `job_files_anon_select` | PERMISSIVE | SELECT | `{anon,authenticated}` | `bucket_id = 'job-files'` | `(null)` |
| `job_files_anon_insert` | PERMISSIVE | INSERT | `{anon,authenticated}` | `(null)` — N/A on INSERT | **`bucket_id = 'job-files'`** |
| `job_files_anon_delete` | PERMISSIVE | DELETE | `{anon,authenticated}` | `bucket_id = 'job-files'` | `(null)` |

On the INSERT policy the gate is `WITH CHECK` alone; its `USING` is `(null)`
because Postgres does not evaluate one on INSERT. Nothing here is read off
`qual`.

**FACT.** Live probe as `anon`: **5 objects listable** in `job-files`, **0** in
`customer-uploads` (which has no policies — correctly closed).

**FACT.** `src/lib/supabase.js:82` — `JOB_FILES_BUCKET = "job-files"`, files at
`jobs/{jobId}/{filename}`, uploaded straight from the browser with the anon key
(`uploadJobFiles`), read back through 1-hour signed URLs.

**FACT.** `print_jobs` is `anon` SELECT `qual=true` **and** `anon` INSERT
`with_check=true`. Live: **6 rows** readable, carrying `customer_name`,
`customer_email`, `customer_phone`.

So an attacker reads `print_jobs` for job ids, lists `jobs/{id}/` directly
through the Storage API, and downloads. No function involved — which is exactly
why fixing the functions does not close this.

**Correction (evidence re-pull, 2026-09-11) — the DELETE claim as first
written was wrong.** This section said `DELETE` "means they can destroy the
store's saved job files", which reads as though the policy alone is the whole
story. Probed as `anon` in a rolled-back transaction:

| probe | result |
|---|---|
| `delete from storage.objects where bucket_id = 'job-files'` | **blocked — `42501 Direct deletion from storage tables is not allowed`** |
| `truncate storage.objects` | **SUCCEEDED, 5 rows → 0** |

The block comes from a Supabase storage **trigger**, not from the policy and
not from RLS. So destruction via plain SQL `DELETE` does not work, and the
earlier wording overstated it. What remains true: `job_files_anon_delete`
still authorises deletion through the **Storage HTTP API** (`storage.remove()`
with the publishable key), which is the path the app itself uses and the path
an attacker would use. The finding keeps its severity; only the mechanism is
corrected. And `TRUNCATE` destroys the whole table regardless — see finding 7.

**Severity: critical**, and independent of finding 1.

### Asked: is `job-files` dead legacy? **No. It is live, and the policy drop would break the app.**

**FACT.** Four helpers in `src/lib/supabase.js` reach the bucket directly with
the anon key. Three have live UI callers today; the fourth has none:

| helper | called from | live caller? | moves server-side in Release 2 |
|---|---|---|---|
| `uploadJobFiles` | `src/App.jsx:2675` (save a print job with attachments) | yes | **yes** |
| `downloadJobFile` | `src/App.jsx:2724`, `src/JobHistory.jsx:298` | yes | **yes** |
| `getJobFileSignedUrl` | `src/JobHistory.jsx:287` | yes | **yes** |
| `deleteJobFiles` | nothing today | no | **yes** |

**Correction (review, 2026-09-10): all FOUR move, not three.** An earlier
revision listed `deleteJobFiles` as a "dead export" and stopped there. Having
no caller is not the same as being out of scope: it is an exported function
holding a direct anon-key DELETE against `job-files`, so it is exactly the
kind of path that gets re-wired in later and silently re-opens the hole after
the policies are closed. It moves server-side with the other three, or it is
deleted outright — a decision for the Release 2 plan, not a reason to skip it.

All live paths go **browser → Supabase Storage with the anon key**, which is
precisely why they depend on `job_files_anon_*`. Dropping those policies today
breaks saving a job with attachments and every download in Job History.

**FACT — what the 5 objects are.** Real customer artwork, not test fixtures.
Every one is referenced by a `print_jobs` row; **zero orphans**:

| object | created | size | type |
|---|---|---|---|
| `jobs/d82ba689…/charly_side_1.jpg` | 2026-06-10 | 9.7 MB | image/jpeg |
| `jobs/d82ba689…/charly_side_2.jpg` | 2026-06-10 | 8.2 MB | image/jpeg |
| `jobs/a7dca7bb…/IMG_7704.PNG` | 2026-05-19 | 2.8 MB | image/png |
| `jobs/d6a4babd…/totalwirelessbackpack-p1.png` | 2026-07-08 | 2.5 MB | image/png |
| `jobs/d6a4babd…/totalwirelessbackpack-p2.png` | 2026-07-08 | 1.6 MB | image/png |

**FACT.** All six `print_jobs` rows carry customer PII (`customer_email` and/or
`customer_phone` non-null). Last upload was 64 days ago, so the feature is live
but low-traffic — low volume, not disused.

**Holding the policy drop, as instructed.** It cannot move before the reads
move server-side, which is the "legacy job history/file access" line in
Release 2. Sequencing it any other way repeats the Aug-31 pattern: revoke
first, discover the client depended on it, restore under pressure.

## Finding 3 — `anon_rw_orders` is ALL / `true` / `true`, and it is not theoretical

**FACT.** Policy `anon_rw_orders`, `cmd=ALL`, `roles={anon,authenticated}`,
`qual=true`, `with_check=true`.

**FACT, executed in a rolled-back transaction as `anon`:**

| probe | result |
|---|---|
| INSERT a forged order (`ATTACKER`, $999.99) | **SUCCEEDED** |
| DELETE a real order (`notes = 'test one'`) | **SUCCEEDED, 1 row destroyed** |
| SELECT all orders | 3 rows, including Phase E `cost_subtotal` / `margin_pct` |

Anyone with the publishable key — which ships in `netlify.toml` and the tracked
`.env`, by design — can read the store's revenue, cost and margin, forge sales
history, and delete real orders.

**Severity: critical.** Phase E made this strictly worse by putting cost and
margin in a table the whole internet can read.

## Finding 4 — PDF.js 3.11.174 is inside the CVE-2024-4367 window

**FACT.** `index.html:9` and `upload.html:8` both pin
`cdnjs.cloudflare.com/ajax/libs/pdf.js/3.11.174/pdf.min.js`.

**FACT.** Five `getDocument` call sites: `src/App.jsx:280`, `src/App.jsx:297`,
`src/BookletMaker.jsx:61`, `src/UploadApp.jsx:73`, `src/DataMerge.jsx:108`.
None passed `isEvalSupported`.

**FACT (public advisory).** CVE-2024-4367: a crafted `FontMatrix` reaches an
eval-like path and executes attacker JavaScript in the page origin. Fixed in
4.2.67. 3.11.174 is before that.

**Why it is reachable here.** Every PDF this app opens is untrusted: staff drop
customer files on the counter iPad, walk-ins upload from `/upload`, and
`fetch-link-job` stores a fetched Google export. Script execution in the app
origin means the anon key, `localStorage` (`currentEmployee`, the offline order
queue), and any live admin session.

**INFERENCE, not executed.** I did not build a weaponised PDF. The conclusion
rests on the version pin plus the published advisory.

**FACT — the option names, probed against the real pdfjs-dist@3.11.174 package**
(installed to a scratch directory, inspected, removed; no dependency added):

| option | read from the getDocument params? | occurrences in pdf.js |
|---|---|---|
| `isEvalSupported` | **yes** — `isEvalSupported = src.isEvalSupported !== false` | 15 |
| `enableXfa` | **yes** — `enableXfa = src.enableXfa === true` | 6 |
| `isXfaEnabled` | **no** | **0** |

So `isEvalSupported: false` genuinely flips a default-on behaviour, and
`isXfaEnabled` — which an earlier revision of `src/lib/pdfSafe.js` passed —
**is not a pdf.js parameter at all**. It was silently ignored, and the test
asserting it only proved the object contained a key we had invented. Corrected
to `enableXfa`. Caught in review, not by me.

**FACT.** A real one-page PDF, constructed inline, opens and its text extracts
correctly through `getDocument({ data, isEvalSupported: false, enableXfa: false })`
on pdfjs 3.11.174 in Node. That proves the options are accepted and parsing
still works. It does **not** characterise how a font-heavy PDF *renders* in a
browser with the eval path disabled — that is the human check the PR asks for.

**Status: mitigated in this branch.** All five sites now go through
`openPdf()` in `src/lib/pdfSafe.js` with `isEvalSupported:false` and
`isXfaEnabled:false`. `scripts/tests/pdf-safe.test.js` fails the build if a raw
`getDocument(` reappears. The upgrade past 4.2.67 stays open: 4.x changes the
worker bootstrap and the `render()` signature and needs a visual pass on all
five sites.

## Finding 5 — the service worker cached API and file responses indefinitely

**FACT.** `public/sw.js` at `30a0aa6`, lines 55-72: for every non-navigation
request it did `caches.match(req)` first, then cached **any** `res.ok`
response, from any origin, with no allowlist.

That means Supabase REST GETs (`orders`, `pending_jobs`, `settings`) and
**signed-URL file responses** were written to `print-app-v14` and served from
it afterwards. A signed URL expires in 15 minutes; the cached copy never
expires. On a shared counter iPad, signing out or switching staff left the
previous session's data — and the previous customer's file — served from cache.

**FACT.** `activate()` (line 22) already deletes every cache whose key is not
the current one, so a cache-name bump *is* the migration. The old code just
never bumped.

**Status: fixed in this branch.** `public/sw.js` is now allowlist-only: same-origin
build output plus three exactly-pinned CDN library URLs. Netlify functions,
Supabase (REST, Storage, Realtime, signed URLs), `pricing.json`, any request
with a query string, any credentialed request and any non-GET are never
intercepted. Cache bumped to `print-app-v16`, which purges both v14 and the flawed v15 on activation.
A `CLEAR_CACHES` message handler is added for sign-out.
`scripts/tests/sw-cache.test.js` asserts all of it.

**Correction (review, rev 2).** An earlier revision of this document and of the
commit messages said the `CLEAR_CACHES` acknowledgement bug meant the feature
"never worked at all". That overstates it. The worker's handler always ran the
purge — `caches.delete` executed regardless of where the reply went. What
failed was only the acknowledgement: it was posted to `event.source` while the
caller listened on a transferred `MessagePort`, so `clearAppCaches()` timed out
and reported `false` even though the caches had in fact been cleared. The
defect was real and worth fixing; the description was not accurate.

**Cache generation.** The corrected worker is `print-app-v16`, not v15. The
first corrected revision reused v15 — the same name the flawed revision used —
so `activate()` would have preserved the exact cache that could hold a poisoned
shell. Production never ran v15; only browsers that opened the rev-1 preview
did. Both upgrade paths (v14 and the flawed v15) are covered by
`scripts/manual/sw-upgrade-check.mjs`, 32/32 in a real browser with two tabs.

### Asked: is `CLEAR_CACHES` wired, or only implemented? **It was only implemented. Now wired.**

**FACT (before this commit).** `grep -rn "CLEAR_CACHES" src/` returned nothing.
The only service-worker reference in the client was registration in
`src/main.jsx:22`. The handler existed and nothing on earth called it.

**Fixed in this commit.** `src/lib/swCache.js` exports `clearAppCaches()`,
called from both handover paths in `src/App.jsx`:

- `handleAdminSignOut` — an owner/manager signing out,
- `switchEmployee` — the counter handover, which is the likelier of the two.

It waits on `navigator.serviceWorker.ready` (a freshly loaded page can have a
null `controller`), replies over a `MessageChannel`, and resolves `false` after
1.5 s. Sign-out never blocks on it and it never throws.
`scripts/tests/sw-clear-caches.test.js` asserts the message, the acknowledgement,
the no-service-worker path, and — the point of the question — that **both call
sites exist**.

## Finding 6 — uploads are unbound: any caller, any path, any volume

**FACT.** `start-upload.js:35-45` takes `fileName`, mints a signed upload URL
at `{date}/{uuid}-{safe}` and returns it. No caller identity, no session, no
quota, no rate limit, no MIME check. `customer-uploads` has
`file_size_limit = null` and `allowed_mime_types = null` (live).

**FACT.** `register-job.js:55-115` takes a caller-supplied `files[]` array and
writes it to `pending_jobs` verbatim. Nothing ties those paths to the uploads
this caller actually made.

**FACT.** `fetch-link-job.js:71-75` still computes `queue_number` with
`count(*)` and **does not stamp `store_id`/`org_id`** — it was missed by the
`register-job` rework merged in #37. On a second tenant it will both collide
and mis-attribute.

**INFERENCE.** Unmetered anonymous writes to a bucket with no size cap are a
cost and denial-of-service exposure. I did not test the limit.

## Finding 7 — NOT in the six-item scope: `anon` holds TRUNCATE, which RLS cannot filter

**FACT.** `information_schema.role_table_grants` for grantee `anon` shows
`TRUNCATE` (with INSERT/UPDATE/DELETE/REFERENCES/TRIGGER) on **every** public
table, including `employees`, `memberships`, `stores`, `settings`,
`sheet_prices`, `orders`, `_archive_commission_columns`.

**FACT, executed as `anon` in a rolled-back transaction:**

| probe | result |
|---|---|
| `UPDATE employees SET pin='0000'` | **blocked by RLS** (0 rows) — the 03b lockdown holds |
| `TRUNCATE employees` | **SUCCEEDED, 2 rows → 0** |
| `TRUNCATE orders` | **SUCCEEDED, 3 rows → 0** |
| `TRUNCATE storage.objects` (added 2026-09-11) | **SUCCEEDED, 5 rows → 0** |
| `UPDATE storage.buckets SET public = true` (added 2026-09-11) | blocked — 0 rows, RLS on with zero policies |
| `SELECT ... FROM storage.buckets` (added 2026-09-11) | 0 buckets visible |

`TRUNCATE` is a table-level privilege and **RLS does not apply to it**. So the
Phase B 03b lockdown, which is the control protecting employee PINs, is
bypassed entirely by a verb it never considered.

**It reaches storage too.** `anon` holds the same grant set on
`storage.objects` and `storage.buckets`. The trigger that blocks a direct SQL
`DELETE` on `storage.objects` (finding 2) does **not** intercept `TRUNCATE`:
the probe emptied the table. One statement destroys every stored customer file
in both buckets.

**The bucket-flip attack is closed**, and this is worth stating because the
grant makes it look open. `storage.buckets` has RLS enabled with **zero
policies**, so as `anon` a `SELECT` returns nothing and an `UPDATE ... SET
public = true` on `customer-uploads` matched no rows. Holding the grant is not
the same as passing the policy check, and here there is no policy to pass.

**INFERENCE — reachability is NOT established.** PostgREST exposes no TRUNCATE
verb, so I could not reach this with the publishable API key. It requires a
direct Postgres connection as `anon`, which needs database credentials. Treat
it as a latent privilege that should not exist, not as a live remote exploit.

**Fix is one migration and carries no client risk**: revoke TRUNCATE (and the
unused REFERENCES/TRIGGER) from `anon` and `authenticated`, on the public
schema **and on `storage.objects`**. Nothing in the app uses them.

## Finding 8 — `stores.bootstrap_secret_hash` is world-readable

**FACT.** Policy `stores_read` is `SELECT` / `{anon,authenticated}` /
`qual=true`, and the column is on the same row. Live probe as `anon` returned
the hash: `b14b900fe398…`.

The plaintext was deliberately never shared and only the SHA-256 was stored.
Publishing the hash hands an attacker an offline brute-force target and removes
the only reason the hashing helped. `anon` needs `stores` for the store profile
(name, address, logo) — it does not need this column.

**Fix**: a view or a column-scoped policy, so anon reads the profile and never
the hash.
